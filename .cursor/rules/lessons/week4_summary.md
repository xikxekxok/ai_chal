## Главная тема недели

Четвёртая неделя посвящена **Model Context Protocol (MCP)** — открытому стандарту, который связывает AI-приложения с внешними инструментами и данными.

LLM сама по себе не знает актуального состояния корпоративных систем, таск-трекеров, репозиториев, календарей, внутренних файлов и CI/CD. MCP вводит общий слой: **host с LLM** использует **MCP client**, **server** публикует доступные tools, а **handler** переводит tool call в конкретный API request, CLI-команду или вызов внутренней функции.

MCP особенно полезен для корпоративных систем, баз знаний, репозиториев, DevOps, календарей, почты и сложных приложений вроде CRM, 1C или SAP.

## Архитектура MCP

Три роли:

1. **Host** — AI-приложение с LLM (Cursor, Claude Desktop, собственный агент).
2. **Client** — часть host, которая общается с MCP server по протоколу.
3. **Server** — публикует tools, resources и prompts; handler выполняет конкретные операции.

**Tool** — отдельная операция с именем, description и input schema. Server может предоставить только безопасное подмножество возможностей, например чтение без записи.

Главный mapping выполняет **handler**: формальный tool call превращается в конкретный HTTP request, CLI-команду или внутренний вызов.

В Kotlin-примере лекции MCP server создаётся через SDK и stdio transport. Tool `get_forecast` принимает latitude и longitude, валидирует их, вызывает Ktor HTTP client для weather API и возвращает `CallToolResult` с `TextContent`.

**Remote MCP Server** требует размещения, реализации протокола, доступа к backend, authentication, TLS, publication и подключения к AI host.

## MCP и API

MCP **не является framework** и **не заменяет API**. SDK на Kotlin, Python или TypeScript лишь реализуют протокол.

API остаётся интерфейсом конкретного backend, а MCP server адаптирует его для AI hosts. Благодаря этому одну интеграцию можно подключать к нескольким совместимым клиентам, не реализуя отдельную связь для каждой пары «модель — сервис».

MCP упрощает повторное использование интеграций, но добавляет server infrastructure, security risks и token overhead.

## Tools и транспорт

- **JSON-RPC 2.0** задаёт форму сообщений.
- **stdio transport** — для локального subprocess.
- **remote transport** — для сетевого сервера (Streamable HTTP и др.).

Формат сообщений и способ доставки — разные уровни.

Для защищённых remote-вариантов дополнительно нужны authentication, TLS, scopes и audit.

**Day 16** (первый практический шаг) проверяет публичный no-auth remote server: подключение к публичному DeepWiki MCP по Streamable HTTP, initialization, discovery через `tools/list` без вызова tools, фактический tool schema и обработка сетевых ошибок.

Локальный stdio server, validation tool calls и token flow относятся к следующим практическим заданиям.

## Безопасность

Безопасность нельзя сводить к наличию schema. Внешний текст может содержать **prompt injection**, а неосторожный handler — передать вредоносное значение в shell или критический API.

Практическая защита включает:

- least privilege;
- read-only режим;
- строгую validation;
- allowlists;
- sandbox;
- timeouts;
- audit log;
- отдельные credentials;
- подтверждение destructive actions.

Для каждого tool нужно определить владельца, scope, validation, error model и правила logging.

## Практические выводы

Начинать внедрение стоит с одного ограниченного **read-only use case**: поиска по базе знаний, получения задач или состояния pipeline.

После этого можно измерять ценность:

- время выполнения;
- долю успешных операций;
- token cost;
- количество заблокированных опасных запросов.

MCP полезен не только как техническая интеграция, но и как **организационный механизм**. Команда может публиковать внутренние tools, подключать корпоративный AI, обучать пользователей и формировать центр компетенций.

При этом естественный язык не отменяет бизнес-правила: агент должен соблюдать те же ограничения доступа, что и обычные клиенты системы.

Для AI Advent Challenge важно **сравнивать подходы воспроизводимо**. Одинаковую задачу следует запускать через MCP и Skill + CLI, фиксируя schemas, число sampling calls, tool results, итоговые prompt tokens и удобство эксплуатации.

## Token overhead и риски

Token cost появляется прежде всего в **sampling calls** к LLM. В prompt входят system instructions, user input, история, tool schemas и результаты предыдущих операций. При длинной цепочке каждый следующий шаг может повторно передавать растущий контекст.

Основные источники overhead:

- **idle overhead** — descriptions и schemas присутствуют, хотя конкретные tools не используются;
- **batching overhead** — множество отдельных действий порождает повторные calls и накопленную историю;
- **schema weight** — большое количество подробных tools увеличивает input.

Пример лекции использует system prompt около 1500 токенов, user input около 200, шесть schemas суммарно около 5400, tool result около 3500 и response около 600. Это иллюстрация масштаба, а не точный benchmark: числа частично уточняются по ходу объяснения.

Универсального квадратичного закона для MCP нет; результат зависит от host, caching, compacting, модели и сборки prompt.

Дополнительное ограничение — MCP server не всегда оправдан. Если один локальный агент работает с простым личным сервисом, прямой API или существующий CLI может потребовать меньше кода и контекста.

## MCP vs Skill + CLI

**MCP** лучше подходит для:

- удалённых серверов;
- публичных tools;
- нескольких AI hosts;
- централизованных credentials;
- формальных schemas.

**Skill + CLI** часто выгоднее в локальной среде, где:

- готовая утилита уже установлена;
- инструкции загружаются on demand;
- несколько операций можно batch-ить;
- idle overhead равен нулю.

Тезис «MCP deprecated» не означает отмену технологии: он подчёркивает, что для части локальных и CLI-задач MCP может быть дороже и сложнее.

Практический выбор определяется **topology**, **security model**, **повторным использованием** и **измеренным token flow**.

## Практический вывод

MCP — это стандартный слой между AI host и внешним миром, а не замена API. Хорошая интеграция начинается с узкого read-only use case, явных schemas, validation и измерения token cost.

К концу недели нужно уметь подключать public MCP, писать свой server, оркестрировать tools в агенте и осознанно выбирать между MCP и Skill + CLI — с фиксацией метрик, а не на ощущениях.
